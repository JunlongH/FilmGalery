# Phase 2+ 分层路线图

> **来源**: 由 `FOLLOWUPS.md` 的「需独立推进的大工程（Phase 2+）」拆分而来。
> **范围**: 10 项跨数周、需架构决策的工程，按依赖关系与风险重组为 4 个阶段。
> **原则**: Phase 0–1 已完成安全/卫生收口；本阶段所有改动**必须在测试护栏就位后**推进，禁止盲改。

---

## 1. 分层模型

| 阶段 | 名称 | 包含工程（原 FOLLOWUPS 编号） | 性质 |
|---|---|---|---|
| **2A** | 基础层 | #10 测试/lint 护栏 · #9 monorepo 收敛 | 前置条件，阻塞其余 |
| **2B** | 安全闭环层 | #1 认证体系 · #7 HTTPS / 移动明文流量 | 偿还 Phase 1 显式 deferred 的安全债 |
| **2C** | 重构层 | #4 错误处理统一 · #5 像素管线下沉 · #6 DB schema 收敛 | 机械/性能重构，需 #10 先行 |
| **2D** | 平台升级层 | #2 Electron 升级 · #3 CRA→Vite · #8 GPU worker 重构 | 高风险，需全量回归 |

每阶段一个独立文件：

- `phase-2a-foundation.md`
- `phase-2b-security.md`
- `phase-2c-refactor.md`
- `phase-2d-platform-upgrade.md`

**关键依赖链**
- `#10 → {#4, #5, #6, #2}`：所有大规模机械重构/升级均以测试护栏为硬前置。
- `#1 ∥ #7`：同源（混合模式安全），Phase 1 的 CORS 决策把远端防御整体押在 #1 上。
- `#8` 是 Phase 1「imageUrl 白名单堵 SSRF」的正式收尾。
- `#9` 的 `packages/shared` + `@filmgallery/api-client` 被三端共用，越早落地越减负。
- `#3` 依赖 `#9` 程度低，可独立并行；但建议在 monorepo 收敛后再做以避免重复迁移。

## 3. 推进顺序建议

```
2A.1+2A.2 (测试/CI 护栏) ──→ 2B (#1+#7 并行) ──→ 2D #2 (EOL 风险) ──→ 2C (#4/#5/#6/#8) ──→ 2D #3 (Vite)
        │
        └─→ 2A.3 (共享包采用+去重) ─────────────────┐
                                                   └─ 与 2B/2C 并行（不阻塞）
```

> **细化（2A 设计验证后）**：2A 拆为 `2A.1/2A.2`（测试+CI 护栏）与 `2A.3`（共享包去重）。**只有 2A.1+2A.2 是 2B 的硬前置**——因为 2B 是新代码（auth+HTTPS），不依赖 monorepo 收敛。2A.3 可与 2B/2C 并行。详见 `phase-2a-foundation.md`。

**理由**
1. **2A.1+2A.2 先行**：作者在 FOLLOWUPS 反复声明「建议在有测试后做」，是后续一切的护栏；且本仓库现状是 `continue-on-error:true` 导致测试不阻断——这是护栏的第一性缺口。
2. **#1 提到 2B 最前**：在认证落地前，远端访问实质无防御（Phase 1 CORS 决策），属最高杠杆。
3. **#2 提到 2D 最前**：Electron 26 已 EOL，安全 CVE 不再 backport，是隐性定时炸弹；但必须测试护栏先到位以支撑 native 重编回归。
4. **#3 最后**：`lazyRoutes.js` 已就绪，迁移成本相对独立，可放在最后吃代码分割红利。

## 4. 跨阶段约束（适用于所有阶段）

- **每阶段开工前**：确认上一阶段验收标准已达成（见各文件末「验收标准」）。
- **每阶段交付物**：① 代码 ② 测试 ③ `FOLLOWUPS.md` 对应条目状态更新 ④ 本目录相关文件打 ✅。
- **回滚预案**：2D 平台升级层每项必须有 feature flag 或独立分支，失败可即时回退。
- **范围纪律**：禁止跨阶段捎带改动；安全问题在任意阶段发现时走独立 hotfix，不并入大工程分支。
